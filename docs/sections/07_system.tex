\section{システム実装上の考察}\label{sec:system}

本章では、\cref{sec:synthetic,sec:empirical}の結果をもとに、提案手法を金融機関のリスク管理システムに組み込むときの設計を論じる。
想定するのは、毎営業日の夜間に、多数の銘柄（あるいはポートフォリオのリスクファクター）について SV モデルを推定し直し、翌日のボラティリティと VaR を出す、という使い方である。
\cref{sec:sys-architecture}でシステムの全体像を示し、
\cref{sec:sys-impl}で実装の要点を、
\cref{sec:sys-warm}で日次の再推定（warm start）を、
\cref{sec:sys-multi}で多銘柄の一括処理を、
\cref{sec:sys-monitor}で収束の判定と品質の監視を、
\cref{sec:sys-repro}で再現性と監査への対応を、
\cref{sec:sys-roles}で MCMC との使い分けを、それぞれ実測の結果に基づいて述べる。

計時はすべて、これまでの章と同じ 1 台の CPU マシン（12 コア、WSL2、GPU なし）で行った。
多銘柄の並列処理では、JAX に CPU を 8 つのデバイスとして見せている。
数値は手法・設定どうしの相対的な比較として読んでほしい。

この構成の要点は三つある。

第一に、\textbf{日々の推定の「状態」は変分パラメータだけ}である。
提案族の変分パラメータは、大域パラメータの平均（3 個）とコレスキー因子（$3 \times 3$）、擬似観測とその精度（各 $T$ 個）で、
推定窓 $T = 250$ なら $2T + 12 = 512$ 個の実数、倍精度で約 4 KB である。
これを銘柄ごとに保存しておけば、翌日はそこから最適化を再開できる（\cref{sec:sys-warm}）。
MCMC のサンプル（$h_{1:T}$ を含めると数千 $\times$ $T$ 個）を保存するのに比べて、はるかに小さい。
最適化手法（Adam）の内部状態は引き継がず、毎日新しく初期化している。

第二に、\textbf{日次の処理は VI だけで完結し、NUTS は週次の検証に回す}。
日次の処理を NUTS で行うと、本稿の 32 銘柄でも 1 回あたり約 5 分（1 銘柄ずつの逐次実行）かかり、しかも連鎖の長さが足りないと収束の診断に引っかかる（\cref{sec:sys-roles}）。
VI を日次の主役にし、NUTS は VI の品質を確かめる「監査役」として使う。

第三に、\textbf{毎回ゼロからの再推定を定期的に行う}。
warm start は前日の結果に依存するので、何らかの理由で局所的な解に入り込むと、それが翌日以降に引き継がれる可能性がある。
毎回ゼロからの推定と定期的に比べることで、これを検出できる。

\subsection{実装の要点}\label{sec:sys-impl}

\paragraph{1 系列の推定を 1 つの純粋関数にする}
本稿の自前実装（\code{advi.py}、約 240 行）では、1 系列の推定全体を、
変分パラメータの初期値・データ・乱数のキーを受け取り、最終の変分パラメータと ELBO の推移を返す 1 つの純粋関数として書いている（\cref{sec:inf-advi}）。
最適化のループ（各ステップで ELBO の勾配を計算し、Adam でパラメータを更新する）は、JAX の \code{lax.scan} で書いてあり、
ループ全体が 1 回の JIT コンパイルで 1 つの計算に変換される \parencite{bradbury2018}。
Python のループで 1 ステップずつ関数を呼ぶ書き方に比べて、呼び出しの手間がなくなり、1 ステップが数十マイクロ秒で回る。
純粋関数として書いてあるので、多銘柄への拡張（\cref{sec:sys-multi}）も、関数を銘柄の方向に写像するだけで済む。

\paragraph{コンパイルの時間とキャッシュ}
JIT コンパイルには約 2 秒かかる（\cref{sec:syn-scaling}）。
コンパイルの結果は、引数の形（系列長 $T$、変分パラメータの形）と静的な設定（変分族、ステップ数など）ごとにキャッシュされ、同じ形の推定を繰り返すときは再利用される。
推定窓の長さを固定したローリング推定では、毎日同じ形になるので、コンパイルは初日だけで済む。
\cref{sec:emp-var}のバックテストで 1 日あたり 0.10 秒になったのは、このためである。
逆に、銘柄ごとに系列長が違うと、長さごとにコンパイルが発生する。
上場が新しい銘柄などで系列長が違う場合は、短い系列を固定長に揃えて欠けた部分をマスクする（尤度を 0 にする）か、系列長をいくつかの区分に丸めてコンパイルの回数を抑えるのがよい。
また、JAX の先行（AOT）コンパイルの機能を使えば、夜間バッチの開始時に必要な形をまとめてコンパイルしておき、その時間を処理の時間と分けて管理できる。

\paragraph{倍精度}
SV モデルの尤度は $y_t^2 e^{-h_t}$ を含み、$h_t$ が小さい（ボラティリティが低い）日には大きな値になる。
単精度（float32）では、ELBO の勾配の計算で桁落ちや溢れが起きやすいため、本稿ではすべて倍精度（float64）で計算している。
CPU では倍精度による速度の低下は小さい。
GPU では単精度の方が大幅に速いことが多いので、GPU で動かす場合は、単精度で十分な精度が出るかを別に確かめる必要がある。

\paragraph{$O(T)$ の計算}
提案族の計算は、三重対角行列のコレスキー分解と前進・後退代入（\cref{sec:fam-conditional}）だけからなり、$T \times T$ の密行列は一度も作らない。
メモリの使用量も $O(T)$ である。
\cref{sec:syn-scaling}で見たように、$T = 10{,}000$ でも 1 回の推定は 10 秒程度で、日次の運用で問題になる長さではない。

\paragraph{自前実装とライブラリ}
同じ変分族は NumPyro のガイドとしても実装でき、結果は自前の実装と一致した（\cref{sec:syn-agreement}）。
NumPyro を使うと、モデルの変更（たとえば誤差分布の差し替え）が容易で、MCMC と同じモデルの記述を共有できるという利点がある。
一方で、\cref{sec:syn-scaling}の計測では、NumPyro の SVI は自前の実装より 1.1〜2.5 倍時間がかかり、最適化ループの細部（コンパイルの単位、warm start のための変分パラメータの受け渡し）を制御しにくい。
本稿では、モデルの開発と検証には NumPyro を、日次の運用には自前の実装を使う、という分担を勧める。
いずれの場合も、依存するライブラリのバージョンはロックファイル（本稿では \code{uv.lock}）で固定し、バージョンを上げるときは、固定したデータでの推定結果が変わらないことを回帰テストで確かめる。

\subsection{日次の再推定と warm start}\label{sec:sys-warm}

\subsubsection{仕組み}

推定窓を 1 日進めると、窓の先頭の 1 日が抜け、末尾に新しい 1 日が加わる。
大域パラメータ $\theta$ の事後分布は、250 日のうち 1 日が入れ替わるだけなのでほとんど変わらない。
潜在ボラティリティ $h_t$ の事後分布も、新しい日の近くを除けば前日とほぼ同じである。
そこで、前日の変分パラメータを次のように「1 日ずらして」新しい日の初期値にする（\code{advi.shift\_params}）。

\begin{itemize}
  \item 大域パラメータの変分パラメータ（$q(u)$ の平均とコレスキー因子）は、そのまま引き継ぐ。
  \item 時点ごとの変分パラメータ（擬似観測 $\tilde y_t$ とその精度 $\lambda_t$）は、先頭の 1 日分を捨てて 1 つずつ前にずらし、末尾の新しい日には前日の最終日の値を複製する。
    $h_t$ は持続性が高いので、昨日のボラティリティは今日のボラティリティのよい初期値になる。
  \item レバレッジ SV の擬似ショック $\tilde e_t$ も同様にずらし、新しい日の分は 0 から始める。
\end{itemize}

この初期値から、毎回ゼロからの推定（10,000 ステップ）よりずっと少ないステップ数で最適化する。

\subsubsection{効果}

\cref{sec:emp-var}のローリング推定（2 銘柄 × 235 日）で、warm start（2,000 ステップ）と毎回ゼロから（10,000 ステップ）を比べた結果を整理する。

\begin{itemize}
  \item \textbf{時間}：1 日あたりの推定時間（中央値）は、毎回ゼロからの 0.54 秒に対して warm start で 0.10 秒と、約 1/5 になった。
  \item \textbf{ELBO}：両者の最終的な ELBO の差（warm start $-$ 毎回ゼロから、最後の 200 ステップの平均）は、日ごとの中央値で $-0.04$〜$+0.02$ nats、90\% の日で $\pm 1$ nats 程度の範囲に収まった。
    200 ステップの平均にも 0.5 nats 程度の雑音があるので（下記）、両者は同じ水準の解に到達していると言える。
  \item \textbf{パラメータ}：$\phi$ の事後平均の差は日ごとの中央値で 0.003〜0.004、$\sigma$ の差は 0.008 程度である。
    これは\cref{sec:emp-full}の事後標準偏差（$\phi$ で約 0.05、$\sigma$ で約 0.08）の 1 割程度である。
  \item \textbf{VaR}：5\% VaR の差の絶対値は、中央値で 0.02〜0.03\% ポイント、95\% 点で 0.08〜0.10\% ポイント、最大で 0.25\% ポイントである。
    VaR の水準（2〜3\%）に比べて小さく、バックテストの結果（超過回数・予測スコア）にもほとんど差がなかった（\cref{tab:var-backtest}）。
\end{itemize}

ステップ数を減らすと、1 日あたりの時間はステップ数にほぼ比例して短くなる（100 ステップで 0.006 秒、1,000 ステップで 0.055 秒、2,000 ステップで 0.10 秒）。
一方、毎回ゼロからの推定との差は、ステップ数が少ないほど大きくなる。
\begin{itemize}
  \item \textbf{100〜250 ステップ}：5\% VaR の差の中央値は 0.06〜0.14\% ポイントであるが、95\% 点は 0.35〜0.56\% ポイント、最大は 0.7〜1.3\% ポイントに達する。
    VaR の水準（2〜3\%）に対して最大で数十 \% の違いであり、日によっては前日の解から十分に動けていない。
    とくに、大きなリターンが窓に入った日や窓から出た日に差が大きくなる。
  \item \textbf{500 ステップ}：差の中央値は 0.04〜0.05\% ポイント、95\% 点は 0.20\% ポイントで、まだ 2,000 ステップより明らかに大きい。
  \item \textbf{1,000 ステップ}：差の中央値は 0.02〜0.03\% ポイントと 2,000 ステップとほぼ同じで、95\% 点も 0.10〜0.14\% ポイントである。
    ただし最大は 0.23〜0.40\% ポイントと、2,000 ステップ（0.14〜0.25\% ポイント）よりやや大きい。
  \item \textbf{2,000 ステップ}：差の 95\% 点は 0.08〜0.10\% ポイントで、最大でも 0.25\% ポイントである。
\end{itemize}
超過回数（14〜18 回）と予測スコアは、ステップ数によってほとんど変わらなかった。
235 日のバックテストの集計値では差が見えにくくても、日々の VaR の値には差が出ていることに注意したい。

なお、$\phi$・$\sigma$ の事後平均の差は、1,000 ステップ以上では 0.003〜0.008 と、ステップ数を増やしてもそれ以上は小さくならない。
これは、毎回ゼロからの推定と warm start の推定がそれぞれ別の乱数を使っていることによる、モンテカルロの雑音の水準である（\cref{sec:sys-repro}で見るように、乱数のキーを変えただけで $\phi$・$\sigma$ の事後平均は 0.002 程度ばらつく）。
VaR の差にも、予測分布を 1,000 個のサンプルで作ることによる雑音が含まれている。

以上から、本稿の設定（推定窓 250 日）では、warm start のステップ数は 1,000〜2,000 が妥当である。
1 銘柄あたりの時間の差（0.05 秒と 0.10 秒）は、数千銘柄でも数分の違いにしかならないので、本稿では安全側の 2,000 ステップを標準とする。


\subsubsection{warm start での収束の判定}

warm start では、\cref{sec:inf-diagnostics}の ELBO による収束の判定（200 ステップごとの ELBO の平均の相対変化が $10^{-4}$ を下回る）がうまく働かない。
2,000 ステップの warm start では、判定が出る前に最適化が終わった日が全体の半分以上あった（収束したステップの中央値が 2,000）。
これは、最適化が進んでいないからではなく、判定の閾値が ELBO の推定値の雑音に比べて小さすぎるためである。
\cref{sec:emp-full}の全期間の推定（$T = 485$）で、収束した後の ELBO の推定値を調べると、
1 ステップごとの推定値の標準偏差は約 8 nats、200 ステップの平均どうしの差の標準偏差でも約 0.7 nats ある。
一方、判定の閾値は ELBO の $10^{-4}$ 倍、すなわち $0.08$ nats 程度である。
したがって、ELBO が平らになった後は、隣り合う 2 つの窓の平均の差がたまたま閾値を下回ったときに判定が出る（1 回の確認あたり 1 割程度の確率）ことになり、
収束と判定されるステップは、ELBO が平らになった時点からランダムに遅れる。
毎回ゼロからの推定では、最初の数千ステップで ELBO が大きく変化するので、判定は「平らになった後のどこか」を示す目安として意味を持つが、
\cref{sec:syn-scaling}で見た収束までの時間のばらつき（$T = 2{,}000$ で 800 ステップ、など）の一部は、この偶然による。
warm start では、初めから ELBO がほぼ平らなので、2,000 ステップ（判定の機会は 9 回）の間に偶然の判定が出ないことが多い。

warm start の運用では、ELBO の相対変化で止めるのではなく、
(i) 決めたステップ数（本稿の結果からは 1,000〜2,000 ステップ）で止め、
(ii) その結果を、前日の結果や毎回ゼロからの推定と比べて確認する（\cref{sec:sys-monitor}）、
という方式が実用的である。
ELBO の判定を使う場合は、閾値を ELBO の雑音の大きさ（MC サンプル数と系列長に依存する）に合わせて設定するか、窓の平均の差を雑音の標準誤差と比べる（たとえば、差が標準誤差の 1 倍未満の状態が数回続いたら止める）といった、雑音を考慮した判定にする必要がある。判定の改良は、毎回ゼロからの推定の打ち切りにも役立つ（\cref{sec:conclusion}）。

\subsubsection{運用上の注意}

\paragraph{定期的なゼロからの推定}
warm start の結果は前日の結果に依存する。
本稿の 235 日の検証では、warm start が毎回ゼロからの推定から系統的に離れていく様子は見られなかったが、
相場の構造が大きく変わったとき（たとえば\cref{sec:emp-var}で見た、2025 年 4 月の急変が推定窓から外れたとき）には、前日の解が新しい事後分布の良い初期値でなくなる可能性がある。
月次などの頻度で、毎回ゼロからの推定を並行して行い、結果を比べることを勧める（\cref{tab:sys-pipeline}の段階 8）。

\paragraph{窓の長さ}
本稿では推定窓を 250 日に固定した。
窓を固定すると、コンパイルが 1 回で済み、計算時間も一定になる。
一方で、\cref{sec:emp-var}で見たように、1 回の大きなショックが窓に入るか出るかで、パラメータが大きく変わる。
窓を長くする（たとえば 500〜1,000 日）と、この影響は小さくなる。
提案手法の計算量は $O(T)$ なので、窓を 4 倍にしても計算時間は数倍にとどまる。
過去のデータを使って事前分布を設定する（たとえば、長期のデータでの事後分布を、短い窓での事前分布にする）のも一つの方法である。

\paragraph{新規上場・欠損・休場}
新規上場の銘柄は、推定窓が埋まるまで系列が短い。
系列長ごとにコンパイルが発生するのを避けるため、窓の長さに満たない部分をマスクして固定長で扱うのがよい。
売買が成立しなかった日は、その日の観測を欠測として扱う（尤度に含めない）ことで、$h_t$ の推移は状態方程式に従って補間される。
SV モデルは状態空間モデルなので、欠測の扱いは自然である。

\subsubsection{vmap が遅い理由}

vmap が遅い理由を切り分けるため、1 つのデバイスの上で、32 銘柄（各 250 日、2,000 ステップ）を三つの方式で処理する時間を比べた（\cref{tab:multi-scaling}の中段）。
Python のループで 1 銘柄ずつ処理すると 3.76 秒、\code{lax.map} で 1 銘柄ずつ処理すると 3.69 秒で、両者はほぼ同じである。
これに対して、\code{vmap} で 32 銘柄をまとめてベクトル化すると 6.32 秒と、1.7 倍遅かった。
複数のデバイスを使わない場合でも vmap が遅いので、遅さの原因はデバイスへの振り分けとの組み合わせではなく、ベクトル化そのものにある。
また、Python のループと \code{lax.map} がほぼ同じであることから、1 銘柄ごとに関数を呼び出す手間は無視できる大きさである。

ベクトル化が効かない理由について、本稿では内部の計算を詳しく解析していないので、以下は推測である。
提案手法の 1 ステップの計算の中心は、三重対角行列の前進・後退代入で、これは時点 $t = 1, \dots, T$ についての逐次的なループ（\code{lax.scan}）である。
1 銘柄の計算では、ループの各段階はスカラーの演算の短い列であり、CPU のキャッシュの中で完結する。
vmap でベクトル化すると、各段階が長さ 32 のベクトルの演算になるが、1 段階あたりの計算量が小さいため、ベクトル演算による高速化よりも、
ベクトルの並べ替えや中間結果のメモリへの書き出し・読み込みの負担の方が大きくなると考えられる。
いずれにしても、「ベクトル化すれば速くなる」とは限らないことは、JAX でこの種の計算を実装するときの実務上の注意点であり、
本番の環境で方式ごとに計測してから選ぶべきである。

\subsubsection{日次の更新と銘柄数}

日次の運用では、全銘柄を毎回ゼロから推定するのではなく、warm start で更新する。
32 銘柄の直近の窓（250 日）について、初日は全銘柄をゼロから推定し、続く 5 日間は warm start（2,000 ステップ）で更新する処理を、8 デバイスに振り分けて実行した（\cref{tab:multi-scaling}の下段）。
銘柄数を増やしたときの伸び方を見るため、同じ 32 銘柄を 4 倍・16 倍に複製して乱数のキーだけを変えた 128 銘柄・512 銘柄でも測った。
複製は計算時間を測るためだけのものであり、推定結果には意味がない。

warm start による 1 日の更新は、32 銘柄で 1.17 秒、128 銘柄で 5.3 秒、512 銘柄で 18.5 秒（いずれもコンパイルを除く、5 日の中央値）であった。
銘柄数にほぼ比例しており、1 銘柄あたり約 0.036 秒である。
毎回ゼロから（10,000 ステップ）では、32 銘柄で 6.6 秒、512 銘柄で 96 秒（1 銘柄あたり約 0.19 秒）である。
コンパイルは、銘柄数によらず 3〜4 秒で、初日に 1 回だけ発生する。

1 デバイスで 1 銘柄ずつ処理する場合の 1 銘柄あたりの時間（2,000 ステップで約 0.115 秒）と比べると、8 デバイスへの振り分けで約 3.2 倍速くなっている。
8 倍にならないのは、本稿の計算機（WSL2 上の 12 個の論理 CPU）では、物理コアの数やメモリの帯域が頭打ちの原因になっているためと考えられる。
R4 の全期間の推定でも、8 デバイスと 4 デバイスの時間はほとんど変わらなかった。
並列化の効率は計算機の構成に強く依存するので、本番の環境で計測して、デバイスの数を決めるべきである。

\subsubsection{規模の見積もり}

以上の計測から、規模を大きくした場合の所要時間を見積もる。
東京証券取引所のプライム市場の上場銘柄数（約 1,600）を念頭に、2,000 銘柄を推定する場合を考える。

\begin{itemize}
  \item \textbf{提案 VI の日次更新（warm start）}：1 銘柄あたり約 0.036 秒（8 デバイス）なので、2,000 銘柄で約 70 秒である。
  \item \textbf{提案 VI の毎回ゼロからの推定}：1 銘柄あたり約 0.19 秒なので、約 6 分である。初回の導入時や月次の再推定に使う。
  \item \textbf{NUTS}：1 銘柄あたり、推定窓 250 日・各連鎖 1,000 回で約 4 秒、485 日・各連鎖 2,000 回で約 7 秒（4 連鎖を 4 コアで並列）なので、2,000 銘柄を 1 銘柄ずつ処理すると 2〜4 時間かかる。
    コアの数に合わせて複数の銘柄を同時に処理しても、本稿の計算機では 1 時間程度はかかると見込まれ、しかも各連鎖 1,000〜2,000 回では $\hat R$ が目安を超える銘柄が多い（\cref{sec:sys-roles}）。
\end{itemize}

すなわち、提案手法を使えば、2,000 銘柄規模でも、日次の更新は 1 台の CPU マシンで数分以内に収まる。
NUTS は、週次の突き合わせとして全銘柄を回すか、日替わりで一部の銘柄を回す（たとえば 1 日 400 銘柄ずつ、5 日で一巡）運用が現実的である。


なお、本稿では GPU での計測は行っていない。
GPU では、行列演算が中心の計算は大きく速くなるが、提案手法の中心は逐次的な三重対角の代入であり、1 銘柄の計算の中で並列化できる部分は少ない。
多数の銘柄を同時に計算する（ベクトル化する）ことで GPU の並列性を生かせる可能性はあるが、CPU での vmap の結果を見る限り、効果は計測してみないと分からない。
GPU を使う場合は、単精度で十分な精度が出るかの確認（\cref{sec:sys-impl}）とあわせて、事前に計測すべきである。

\subsection{収束の判定と品質の監視}\label{sec:sys-monitor}

VI は、最適化が終われば必ず何らかの答えを返す。
MCMC のように「連鎖が混ざっていない」という形で失敗が目に見えることは少なく、
\cref{sec:syn-agreement}で見たように、平均場の ELBO は順調に収束していながら、事後分布の近似としては大きく外れていた。
したがって、VI を運用するシステムでは、「最適化が終わったか」ではなく「答えが信頼できるか」を確かめる仕組みが必要になる。
本稿では、監視を次の四つの層で考える。

\paragraph{(i) 実行ごとの確認}
各銘柄の推定が終わるたびに、次を確認する。
\begin{itemize}
  \item ELBO と変分パラメータが有限の値か（数値的な発散がないか）。
  \item 最後の数百ステップの ELBO の平均が、前日の値から大きく下がっていないか。
    推定窓が 1 日ずれるだけなので、ELBO は日によって大きくは変わらない。
    本稿のローリング推定では、warm start の ELBO の日次の変化の絶対値は中央値で 0.8 nats、99\% 点で 4〜5 nats であった。
  \item 毎回ゼロからの推定では、ELBO の収束の判定（\cref{sec:inf-diagnostics}）が出ているか。
\end{itemize}

\paragraph{(ii) 推定値の連続性}
パラメータの事後平均、最終日のボラティリティ $h_T$、VaR の日々の変化を監視する。
\cref{fig:monitoring}に、\cref{sec:emp-var}のローリング推定での $\phi$ と $\sigma$ の事後平均の推移を示す。

\begin{figure}[tbp]
  \centering
  \includegraphics[width=\linewidth]{figures/fig7_monitoring.pdf}
  \caption{ローリング推定（推定窓 250 日）でのパラメータの事後平均の推移。
    青の線は提案手法（warm start、毎日）、黒の点は NUTS（5 日ごと）。
    縦の破線は、2025 年 4 月の急落・急反発（4 月 7 日・10 日）が推定窓から外れた日（2026 年 4 月 21 日）。}
  \label{fig:monitoring}
\end{figure}

通常の日には、パラメータの変化は小さい。
$|\Delta\phi|$ は中央値で 0.003〜0.005、99\% 点で 0.02 程度、$|\Delta\sigma|$ は中央値で 0.007、99\% 点で 0.03〜0.05 である。
最も大きな変化（$\sigma$ で 0.08〜0.11）は、両銘柄とも 2026 年 4 月 21 日、すなわち 2025 年 4 月 10 日の急反発が推定窓から外れた日に起きた。
この日の前後数週間で、2025 年 4 月の急変動の期間が少しずつ窓から外れていき、$\sigma$ は約 0.45 から 0.25 に、$\phi$ は約 0.84 から 0.93 に移った。
これはモデルの不具合ではなく、窓を区切った推定の性質であり、データ上の出来事（大きなリターンが窓から外れた）で説明できる。
監視の閾値を、過去の日次の変化の分布（たとえば 99\% 点の 2 倍）に置くと、このような変化は警告として検出されるが、
担当者が原因を確認して「説明のつく変化」として承認する、という運用になる。
閾値を超えた変化の多くは、このように窓への大きなリターンの出入りで説明できるはずであり、説明できない変化が最適化やデータの問題を示す。

\paragraph{(iii) NUTS との定期的な突き合わせ}
VI の近似の質そのものは、NUTS と比べなければ分からない。
週次などの頻度で、全銘柄（または代表的な銘柄）を NUTS で推定し、VI と比べる。
\cref{fig:monitoring}では、提案手法の $\phi$・$\sigma$ は NUTS の推定値の近くを動いているが、$\sigma$ はほぼ一貫して NUTS より少し小さい。
これは\cref{sec:emp-multi}で見た系統的な差（$\sigma$ で約 $-8\%$、$\phi$ で $+0.02$）である。
したがって、突き合わせの閾値は「差が 0 かどうか」ではなく、「差がこれまでの範囲（たとえば $\sigma$ の相対差で $-15\%$〜$0\%$、NUTS の事後標準偏差で基準化して 1 以内）に収まっているか」で設定する。
VaR の水準では、両者の差は 0.02\% ポイント程度（\cref{sec:emp-var}）なので、VaR の差を直接監視するのが最も分かりやすい。
NUTS の側の収束の確認（$\hat R$、ESS）も同時に行い、NUTS が収束していない銘柄は比較から除くか、連鎖を長くして推定し直す（\cref{sec:sys-roles}）。

\paragraph{(iv) VaR のバックテストの継続}
最終的な出力である VaR については、直近 250 日などの窓で、超過回数と Kupiec・Christoffersen の検定（\cref{sec:emp-var}）を毎日計算して監視する。
規制上のバックテストでも、99\% VaR（本稿の 1\% VaR）の超過回数を直近 250 営業日で数える枠組みが使われている \parencite{bcbs2019}。
ただし\cref{sec:emp-var}で述べたとおり、250 日程度では検定の検出力は低いので、検定の結果だけでなく、超過が特定の時期に固まっていないかを目で確認することも重要である。

\paragraph{PSIS $\hat k$ の扱い}
PSIS の $\hat k$（\cref{sec:inf-diagnostics}）は、VI の近似の質を NUTS なしで測れる数少ない指標である。
しかし本稿では、提案手法の $\hat k$ は合成データで 0.85、実データで 0.8〜1.6 と、信頼できるとされる目安の 0.7 を常に超えた（\cref{sec:syn-agreement}）。
$\hat k$ を合否の基準にすると、提案手法はつねに「不合格」になり、監視として機能しない。
本稿では、$\hat k$ は補助的な指標として記録し、値が普段の範囲から大きく外れたときに調べる、という使い方にとどめることを勧める。

\paragraph{異常が見つかったときの対応}
監視で異常が見つかった銘柄については、次の順で対応する。
\begin{enumerate}
  \item 毎回ゼロからの推定（10,000 ステップ）をやり直し、warm start の結果と比べる。warm start の問題であれば、これで解消する。
  \item それでも異常が残る場合は、NUTS で推定し、VI と比べる。データの問題（異常値、調整漏れ）であれば、NUTS でも同じ異常が出る。
  \item 当日の結果を確定できない場合は、前日の結果（変分パラメータ）を使って予測し、その旨を記録する。
\end{enumerate}
\cref{sec:sys-multi}の計算時間から、1 銘柄を毎回ゼロから推定し直すのは 1 秒以内、NUTS でも 10 秒程度であり、少数の銘柄であれば夜間バッチの中で対応できる。

\subsection{再現性と監査への対応}\label{sec:sys-repro}

金融機関でモデルを運用する場合、同じ入力から同じ出力が得られること（再現性）と、出力がどのように得られたかを後から説明できること（監査可能性）が求められる。
金融庁の「モデル・リスク管理に関する原則」\parencite{fsa2021mrm}も、モデルの開発・承認・継続的なモニタリング・検証などについての考え方を示している。
確率的な手法である VI（と MCMC）を使う場合、乱数の扱いがその鍵になる。

\paragraph{乱数のキーの管理}
JAX の乱数は、明示的に渡す「キー」から決定的に生成される。
本稿では、実験の番号・銘柄・日付などの識別子から、シードを起点に決定的にキーを作っている（\code{fold\_in} を重ねる）。
運用でも、銘柄コードと営業日からキーを作り、キーそのものを結果と一緒に保存しておけば、どの日のどの銘柄の結果でも後から再計算できる。

\paragraph{同じキーなら同じ結果になるか}
同じ乱数のキーと同じデータで推定を 2 回行うと、変分パラメータはビット単位で完全に一致した（差の最大は 0）。
また、同じキーを使えば、1 銘柄ずつの逐次実行と、\code{lax.map} による実行、8 デバイスに振り分けた並列実行（\code{pmap} と \code{lax.map}）の結果も、ビット単位で一致した。
したがって、本稿の方式で並列化しても、デバイスの数や銘柄の割り当てによって結果は変わらない。
これは監査の観点から重要な性質である。
一方、\code{vmap} でベクトル化した場合は、逐次実行との差が最大で $2.6 \times 10^{-14}$ あった。
浮動小数点の演算の順序が変わるためで、実用上の影響はないが、「ビット単位で同じ」ことを求める場合には注意が必要である。
なお、ここでの一致は同じ計算機・同じライブラリのバージョンでの話であり、CPU の種類やライブラリのバージョンが変われば、浮動小数点の水準で結果が変わりうる。
そのため、バージョンを固定し、更新の際には回帰テストで差の大きさを確かめる（\cref{sec:sys-impl}）。

\paragraph{乱数によるばらつきの大きさ}
キーを変えると、結果は少し変わる。
1321 の直近 250 日の窓を、キーだけを変えて 10 回推定すると（毎回ゼロから、10,000 ステップ）、
$\phi$ の事後平均の標準偏差は 0.0015（最大と最小の差 0.0055）、$\sigma$ は 0.0019（同 0.0064）であった。
\cref{sec:emp-multi}の 32 銘柄の推定でも、別のキーで行った逐次実行と並列実行の差は、$\phi$ で最大 0.016、$\sigma$ で最大 0.012 であった。
\cref{sec:syn-sensitivity}でも、同じ設定を別の乱数で回すと、事後標準偏差の比が $\pm 0.05$ 程度変わった。
これは、推定の不確実性（事後標準偏差）よりずっと小さいが、結果を報告するときには、乱数による変動があることと、その大きさを把握しておく必要がある。
たとえば、前日との差が乱数による変動と同程度であれば、それは「市場の変化」ではない。

\paragraph{記録しておくもの}
本稿の実験では、各結果に、乱数のシード、設定（ステップ数、学習率、MC サンプル数）、ライブラリのバージョン、デバイスの数、データの取得日と件数を記録している。
運用では、これに加えて、日々の変分パラメータ（約 4 KB/銘柄）と入力データの版（またはハッシュ値）を保存する。
変分パラメータがあれば、事後分布からのサンプルや VaR を後からいつでも再計算できる。

\paragraph{VI に向く用途}
提案手法は、ボラティリティの推定と VaR の予測については NUTS とほぼ同じ結果を、はるかに短い時間で出す。
多数の銘柄を毎日推定し直すという、本稿が想定する使い方には VI が適している。

\paragraph{NUTS が必要な用途}
一方で、パラメータそのもの（とくにその不確実性や、レバレッジの相関 $\rho$）を使う用途では、VI の系統的な差が問題になりうる。
たとえば、推定したパラメータを使ってボラティリティのシナリオを生成する場合、$\sigma$ を約 8\% 小さく推定すると、シナリオのばらつきが小さくなる。
このような用途では、NUTS を十分に長く回すか、少なくとも VI の結果を NUTS で確かめるべきである。

\paragraph{NUTS も万能ではない}
最後に強調しておきたいのは、NUTS も「回せば正しい」わけではないことである。
本稿でも、合成データの 200 回の推定のうち 156 回（\cref{sec:syn-recovery}）、実データの 32 銘柄のうち 11 銘柄（\cref{sec:emp-multi}）で、各連鎖 2,000 回のサンプリングではパラメータの $\hat R$ が目安の 1.05 を超えた。
中心化パラメータ化の SV モデルでは、$\sigma$ と $h$ の強い事後依存のために NUTS の混合が遅い（\cref{sec:model-param}）。
NUTS を正解として使うには、$\hat R$ と ESS を必ず確認し、
連鎖を長くする（本稿の S2・R1b では各連鎖 32,000 回の更新で $\hat R \le 1.004$ になった）、
中心化と非中心化を交互に使う ASIS \parencite{kastner2014}のようなパラメータ化の工夫を取り入れる、などの対策が必要である。
NUTS を「監査役」として使う以上、監査役自身の収束の確認も、監視の一部として組み込んでおく必要がある。

\subsection{まとめ}\label{sec:sys-summary}

本章の要点をまとめる。

\begin{enumerate}
  \item \textbf{日次の運用は VI で完結できる}。
    状態として保存するのは銘柄あたり約 4 KB の変分パラメータだけで、warm start により 1 銘柄 1 日あたり 0.1 秒程度で更新できる。
    ステップ数は 1,000〜2,000 が妥当で、100〜250 では日によって VaR が 1\% ポイント程度ずれる。
  \item \textbf{多銘柄は CPU デバイスへの振り分けで並列化する}。
    32 銘柄の全期間の推定は 15 秒（NUTS の約 19 倍速い）。日次の warm start による更新は 1 銘柄あたり約 0.036 秒（8 デバイス）で、銘柄数に比例して伸び、2,000 銘柄でも約 70 秒と見積もられる。
    vmap によるベクトル化は、この問題では CPU でかえって遅かった。
  \item \textbf{「最適化が終わった」と「答えが信頼できる」は別}。
    実行ごとの確認、推定値の連続性、週次の NUTS との突き合わせ、VaR のバックテストの 4 層で監視する。
    $\hat k$ は補助的な指標にとどめる。warm start では ELBO の相対変化による収束判定は雑音で成立しないので、決めたステップ数で止めて結果を確認する。
  \item \textbf{再現性は乱数のキーの管理で確保できる}。
    同じキーなら結果はビット単位で一致し、本稿の並列化の方式（pmap と lax.map）では、並列化しても結果は変わらない。キーを変えたときのばらつき（$\phi$・$\sigma$ で 0.002 程度）も把握しておく。
  \item \textbf{VI と NUTS は役割を分けて併用する}。
    日次の多銘柄の推定は VI、パラメータの解釈と VI の監査は NUTS。NUTS 自身の収束の確認も欠かせない。
\end{enumerate}
